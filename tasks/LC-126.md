Review the **Latest** section of the Lionscraft website and suggest how that page can be updated in a CMS-ish way — i.e. a repeatable way to publish new entries without hand-editing markup.

## Notes

**What it is today.** `site/latest.html` is a static Webflow export. The section is a hand-written block:

```html
<section class="v2-latest">
  <div class="v2-latest_grid">
    <article class="v2-post">
      <div class="v2-post_meta">Event / ValOS · 29 Oct, 2PM UTC</div>
      <h3 class="v2-post_title">Lido Poolside: ValOS…</h3>
      <p class="v2-post_desc">Our CEO Adi Hussien joins…</p>
      <a href="https://luma.com/c6t2hftd" class="v2-latest_link">Join the panel</a>
    </article>
    … two more …
  </div>
  <div class="v2-latest_foot">… Follow us on LinkedIn …</div>
</section>
```

So one entry = four hand-typed fields (meta line, title, description, link). There are exactly three entries today: Lido Poolside (Event), Understanding digital asset custody (Research), Slashing risk explained (Insights).

**Three problems, in order of how much they hurt:**

1. **The same block is duplicated on the homepage.** `index.html` carries its own `.v2-latest` section. Every new entry has to be added in two files, or the homepage and `/latest` drift apart. That is the real cost — not typing HTML, but typing it twice and keeping them in sync.
2. **Publishing means editing a Webflow export.** A non-technical editor either breaks the Webflow classes or has to ask a dev. There is no "add an entry" action anywhere.
3. **Nothing is dated, so nothing ages out.** The top card is a panel from **29 Oct** — already in the past as of today (2 Nov). With no date field there is no way to sort, and no way to drop stale entries automatically.

**Proposed — three options, cheapest first:**

**Option 1 — git-native data + tiny build (recommended).** One file `site/data/latest.json` holding an array of entries; a ~40-line `scripts/build-latest.py` reads it and replaces only the inner `<div class="v2-latest_grid">…</div>` in `latest.html` **and** the homepage block, leaving all Webflow markup and CSS untouched. Publishing = add one JSON object, run the script, commit. No new service, no account, no cost, no dependencies — and it matches the philosophy already used on the board ("your data as plain files in your own repo"). `<!-- LATEST:START -->` / `<!-- LATEST:END -->` markers make the replacement safe and obvious.

**Option 2 — markdown entries + build.** Same render step, but each entry is `content/latest/<slug>.md` with frontmatter (type, category, date, title, summary, link). More CMS-like; better if entries ever grow into short posts. More files to look after.

**Option 3 — a real editor UI (Decap CMS).** Free, open-source, git-backed: gives a form at `/admin` that commits to GitHub, so a non-technical editor never sees HTML. Best editing experience, but needs GitHub OAuth wiring and adds a small build step. Worth it only if a non-dev will publish regularly.

**My recommendation:** Option 1 now. It is a half-day, zero-dependency change that fixes the duplication and gives entries a `date` so the list can sort itself and past events can drop off. Keep Option 3 in the drawer for when someone non-technical wants to publish without touching the repo.

**One caveat:** the site is a static export served by `serve.py`, so "CMS-ish" must not mean running a CMS server. All three options stay static — the build runs at commit time, the site stays plain HTML.
